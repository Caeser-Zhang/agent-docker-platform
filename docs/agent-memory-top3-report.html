TL;DR核心结论

Agent 记忆赛道的 Top3 由三种根本不同的架构哲学各占一席：Mem0（向量+图+KV 混合存储、LLM 自动提取，"记忆即服务"）、Zep/Graphiti（时序知识图谱、双时间轴事实失效，"记忆即图谱"）、Letta（OS 式分层内存、Agent 自编辑，"记忆即运行时"）。三者在 GitHub 星数上均为 2.4 万+ 量级 A级·API实测，同为本赛道事实标准，选择取决于问题形态而非绝对排名。

⚠️ 所有厂商自报 Benchmark（如 Mem0 宣称 LongMemEval 94.4%）与独立复现（同项目实测 57.5%）存在最高 37 个百分点的差距，且 LoCoMo 基准自身存在约 6.4% 的错误答案键——选型切勿以单一 benchmark 分数为准，详见 第 06 节。

定位："The Memory Layer for your AI Apps"——一个可以五行代码接入任何现有 Agent 的外挂式记忆层，而非重构你的 Agent 运行时。研究论文《Mem0: Building Production-Ready AI Agents with Scalable Long-Term Memory》（arXiv:2504.19413，2025-04-28，已被 ECAI 接收）确立了其学术基础。A级·arXiv

核心机制：两阶段"提取 → 更新"管线

Mem0 的设计哲学是增量处理——每来一轮对话就实时提取和更新记忆，而非批处理整段历史：

图 2 · Mem0 两阶段管线：提取（候选事实）→ 更新（四操作决策）→ 三层存储 → 多信号检索融合 A级 arXiv:2504.19413 + docs.mem0.ai

图增强变体 Mem0ᵍ：在文本事实记忆之外并行维护一张有向标签图——实体提取器识别节点（人/地点/概念），关系生成器推断带标签的边（住在/喜欢/拥有），冲突检测器识别重叠或矛盾的节点与边。论文报告 Mem0ᵍ 比基础版总分高约 2%。A级·arXiv

2026-04 算法换代：官方将更新策略改为单遍 ADD-only 提取（不再覆盖/删除旧事实，Agent 生成的事实与用户事实同权存储），叠加三信号并行检索融合。这一改动直接针对旧版"时序查询弱"的批评——官方报告 temporal 类问题提升 +29.6 分。B级·官方博客，未经同行评审

代码示例（自托管）

from mem0 import Memory
# 初始化：本地 Qdrant 向量库 + OpenAI 抽取模型
m = Memory.from_config({
    "vector_store": {"provider": "qdrant", "config": {"host": "localhost", "port": 6333}},
    "llm": {"provider": "openai", "config": {"model": "gpt-4o-mini"}},
})
m.add("用户后端服务偏好 TypeScript 而非 Python", user_id="alice")   # 写入即触发提取+更新管线
hits = m.search("用户偏好什么编程语言？", user_id="alice")          # 多信号融合检索
优势
  • 社区与生态最大：21+ 官方集成（LangGraph/CrewAI/AutoGen/OpenAI Agents SDK/Dify/Mastra…）
  • 接入成本最低：约 6 行代码，5 分钟完成原型，框架无关
  • 自适应更新：修正偏好时更新既有记忆而非重复追加
  • 用户/会话/Agent 三级记忆命名空间，天然多租户
  • 托管层含 SOC 2 Type II + HIPAA，适配医疗金融合规场景
  • 支持 CLI/Harness/Plugin 形态，可接 Claude Code、Cursor 等编码工具
劣势
  • 时序推理 historically 偏弱：事实"更新"而非带有效性窗口的"版本化"（2026-05 才推出 Temporal Reasoning）
  • 云版定价悬崖：图功能锁在 $249/月 Pro 档，免费/$19 档仅向量检索
  • 每次写入含 LLM 调用（提取+决策），高频写入成本不可忽视
  • 厂商 Benchmark 与独立复现差距大（37 个百分点），数据需谨慎采信
  • 记忆结构相对扁平，复杂关系表达不如图谱路线

适用：个性化助手、客服 Agent、B2B Copilot 等"记住用户偏好与上下文"为核心诉求、希望快速上线的场景。不适用：重度图查询（付费墙）、强时序推理、气隙环境（需自备 Qdrant+Neo4j）。

定位：Zep 是记忆服务，Graphiti 是其开源的时序知识图谱引擎——注意两者开源边界不同：Graphiti 完全开源（Apache-2.0），而 Zep 托管服务（多租户/治理/冲突消解）为商业产品。论文《Zep: A Temporal Knowledge Graph Architecture for Agent Memory》（arXiv:2501.13956，2025-01-20）。A级·arXiv

核心命题：记忆不只是"存了什么"，更是"什么时候为真、什么时候失效"。每条事实边携带有效性窗口（valid_at / invalid_at），新证据到来时旧事实被标记失效而非删除——赋予 Agent"时间穿越"能力：既能答"现在的事实"，也能答"三个月前你基于什么认知做的决定"。

核心机制：三层子图 + 双时间轴

图 3 · Graphiti 三层子图 + 双时间轴 + 混合检索管线 A级 arXiv:2501.13956 + github.com/getzep/graphiti

与 GraphRAG 的本质区别：GraphRAG 面向静态文档语料批量重算；Graphiti 面向持续演化的数据增量实时更新，且矛盾处理是"自动失效 + 历史保留"而非依赖 LLM 摘要判断。查询延迟亚秒级 vs GraphRAG 秒~十秒级。A级·官方仓库

基础设施：支持 Neo4j 5.26 / FalkorDB 1.1.2（含嵌入式 falkordblite）/ Amazon Neptune；Kuzu 后端已弃用（2026-03 起移出测试基础设施）。自定义本体通过 Pydantic 模型定义实体与边类型（prescribed ontology），也可让系统自动发现（learned ontology）。A级·仓库实测

代码示例（Graphiti 开源引擎）

from graphiti_core import Graphiti
graphiti = Graphiti(neo4j_uri, neo4j_user, neo4j_password)
await graphiti.build_indices_and_constraints()
# 摄入一个 episode（对话消息 / JSON / 文本）→ 自动抽取实体与带时间的事实边
await graphiti.add_episode(name="chat-001", episode_body="Alice 已从公司一离职，加入公司二", ...)
results = await graphiti.search("用户现在在哪家公司工作？")
for edge in results:
    print(edge.fact, edge.valid_at, edge.invalid_at)  # 旧边带 invalid_at，新边带 valid_at，历史全保留
优势
  • 时序推理同类最强：事实带有效期窗口，支持"当时 vs 现在"的时间点查询
  • "失效不删除"哲学：完整证据链，适配金融/医疗合规审计
  • 融合对话 + 结构化业务数据（CRM/JSON）到同一张演化图谱
  • 上下文压缩极致：115K → 1.6K tokens，延迟降 90%
  • 引擎完全开源可独立使用，图功能不锁高价档（云版 $25/月起含图）
  • 增量实时更新，无需 GraphRAG 式批量重算
劣势
  • 自托管需运维图数据库（Neo4j/FalkorDB），基础设施门槛高于向量方案
  • 每次摄入含实体抽取+去重+关系更新多次 LLM 调用，写入成本高
  • 实体消解需专项评估：同名合并、别名分裂、否定误判为肯定等风险
  • 完整 Zep 服务（冲突消解、托管图谱）仅云端，开源边界需注意
  • 稳定文档库场景收益有限，时序抽取成本不划算

适用：CRM/销售 Agent（"谁负责什么、从何时起"）、合规敏感系统、状态随时间演化的企业工作流。不适用：仅需"记住名字和偏好"的轻量个性化（用 Mem0 更划算）、纯静态文档问答（用普通 RAG/GraphRAG）。

定位：与前两者根本不同——Letta 不是外挂记忆层，而是"记忆优先"的 Agent 运行时。其他框架"发货编排、让你自己装记忆"，Letta"发货记忆、让你往上装编排"。源自 MemGPT 论文（arXiv:2310.08560，Berkeley，Packer/Wooders/Stoica/Gonzalez 等）提出的虚拟上下文管理：把 LLM 上下文窗口当 RAM，外部存储当磁盘，由模型自己通过工具调用决定分页。A级·arXiv

核心机制：三层记忆层级 + Agent 自编辑

图 4 · Letta 三层记忆层级（MemGPT 虚拟上下文）+ 睡眠计算 + 共享记忆块 A级 arXiv:2310.08560 / 2504.13171 + docs.letta.com

自动上下文管理：Agent 循环持续监控 token 用量，当超出上下文窗口时自动触发压缩（滑动窗口保留近期消息，或全量摘要）。开发者无需手写溢出处理器——这是 Letta 与其他框架最大的单点差异。记忆块（Memory Blocks）是承重原语：带标签的持久化字符串，Agent 用 core_memory_append / core_memory_replace 自编辑，新版本已取消块大小限制（随 128K 上下文窗口自由增长）。A级·官方文档

工具治理：九种工具规则类型（InitToolRule / TerminalToolRule / ConditionalToolRule / RequiresApprovalToolRule 等）提供对 Agent 行为的确定性约束，可精确表达"回答用户前必须先查文档；退出前必须记录日志"式协议。B级·第三方深度评测

2026 演进：① Conversations API（2026-01）——同一 Agent 跨并发会话共享记忆；② Letta Code（2025-12）——记忆优先的编码 Agent，自称 Terminal-Bench 上排名第一的模型无关开源编码 Agent B级·官方博客；③ Context Repositories（2026-02）——基于 git 版本化的编码 Agent 记忆。

性能数据

⚠️ 数据冲突显式标注
Letta 的 LongMemEval 流传数据为 83.2%（源头 Vectorize.io 文章，被多家博客转引 C级·转引），但 Mem0 官方 2026 报告称 Letta "无标准化 LongMemEval 公开结果"，其 LoCoMo 74.0（gpt-4o-mini、文件系统存储、无专用检索工具）C级·竞对转述。第三方独立评测 OmniMemEval 的 BEAM 实测：Letta cloud 100K 规模 nugget 69.22、10M 规模 52.30 B级·独立复现。Letta 团队自己的研究立场是"简单文件存储可与专用检索方案竞争"——其 benchmark 参与度低是路线选择而非能力缺失。

代码示例

# pip install letta && letta server  （本地起服务，状态持久化到数据库）
from letta import create_agent
agent = create_agent(
    name="support_bot",
    model="openai/gpt-4o",
    memory_blocks=[                                # 核心记忆块：Agent 可自编辑
        {"label": "user_preferences", "value": ""},
        {"label": "order_history", "value": ""},
    ],
)
# 用户说"我更喜欢邮件联系" → Agent 自主调用 core_memory_replace 更新 user_preferences 块
# 下次会话自动继承；archival_memory_search 按需从向量库取回长期事实
优势
  • 记忆是框架的一等公民：持久化默认开启，"忘记记忆"需要主动不调用工具
  • Agent 真正"有状态"：以服务形式寻址，跨重启/迁移/时间存续
  • 睡眠计算把推理负载移到空闲期，帕累托改进成本与延迟
  • 共享记忆块是多 Agent 协同的天然基础设施
  • ADE 可视化调试：实时查看上下文窗口、记忆块、归档存储
  • 学术传承最正统（MemGPT 原作者团队），持续产出前沿研究
劣势
  • 运行时锁定：Letta 拥有 Agent 循环，迁出 = 重建 Agent 而非换记忆后端
  • 每轮 token 开销更高、循环更慢（Agent 花推理预算做记忆家务）
  • 学习曲线陡于 drop-in 方案，需理解分层记忆与工具治理
  • 记忆质量强依赖底层模型的编辑能力
  • 公开 benchmark 数据少且互相矛盾，难以横向量化比较

适用：跨周/月运行的个人助理与研究 Agent、需要"Agent 有身份且持续演化"的产品、多 Agent 共享状态场景。不适用：无状态单轮管线、快速原型（用 Mem0）、只需外挂记忆不想换运行时（用 Mem0/Zep）。

06Benchmark 可信度分析（冲突信源显式标注）

这是本报告最重要的一节：Agent 记忆赛道的 benchmark 数据厂商自报与独立复现严重背离，且基准本身存在测量缺陷。以下按可信度分级呈现。

🚨 核心警示：厂商自报 vs 独立复现
唯一的同 harness 多厂商公开复现（Maximem 开放 harness）将 Mem0 的 LongMemEval 从自报 94.4% 拉到 57.5%（差距 36.9 个百分点）；独立 LoCoMo 复现（memnode.dev）为 66.9% vs 自报 92.5。Zep 自报 LongMemEval 71.2%，AgentOS 审计复现为 63.8%。更根本的是：LoCoMo 基准自带约 6.4% 的错误答案键，LLM 裁判会接受约 63% 的错误答案——测量仪器本身是漏的。B级·GenαAI 汇总多方审计
数据点厂商自报独立复现差距可信度判定
Mem0 · LongMemEval94.4%57.5%（Maximem harness）-36.9pp冲突 自报未经同行评审、无公开 harness；复现值更接近其 2025 论文口径
Mem0 · LoCoMo92.566.9%（memnode.dev）-25.6pp冲突 论文原报告单跳 J 分数 67.13，与复现值吻合
Mem0 · LOCOMO vs OpenAI+26%（J 分数）—（论文数据，ECAI 接收）—A级 同行评审论文口径，最可信的 Mem0 数据
Zep · LongMemEval (gpt-4o)71.2%63.8%（AgentOS 审计）-7.4pp部分可信 论文自报但复现差距相对小
Zep · LoCoMo75.14（Zep 口径）/ 94.7%（官网 2026）65.99（Mem0 报告转述）口径混乱冲突 双方互报对方低分，典型的厂商互相贬低
Zep · DMR 94.8% vs MemGPT 93.4%94.8%无（Zep 自己引入的基准）—谨慎 既是运动员又是裁判员；且 DMR 区分度有限
Letta · LongMemEval83.2%（Vectorize 转引）Mem0 报告称"未发布标准化结果"—存疑 源头不可考，Letta 官方立场是"文件存储可与专用检索竞争"
OmniMemEval · BEAM 100K/10MMem0 cloud 70.4/43.3 · graphiti-zep 68.7/56.1 · Letta cloud 69.2/52.3（nugget score）—B级 MemTensor 的第三方统一 harness，目前最接近"公平对比"的公开数据
📌 我们的结论
① 任何单一 benchmark 分数都不可作为选型依据——分数是 harness 相对的，不是系统绝对的；② 在第三方统一 harness（OmniMemEval BEAM）下，三家在 100K 规模差距不大（68.7~70.4），在 10M 超长规模下 Graphiti 自托管反而领先（56.1 vs Mem0 43.3）；③ 可信度排序：同行评审论文（A）> 统一 harness 独立复现（B）> 厂商博客自报（C）> 第三方博客转引（C-）；④ 正确做法：用自己的真实对话记录跑自己的召回评测（run your own recall eval）。

07选型决策指南

如果你的场景是…首选理由
快速给现有 Agent 加个性化记忆（5 分钟原型）Mem0drop-in SDK，接入成本最低，免费档足够验证
"用户上周二时的状态是什么"式时间点查询Zep / Graphiti双时间轴 + 事实失效是独有能力，其他方案无法原生回答
CRM/销售 Agent：谁负责什么、从何时起、何时交接Zep / Graphiti实体关系 + 有效期窗口天然匹配组织状态演化
跨周/月运行的个人助理，Agent 需有持续演化的身份Letta记忆即运行时，Agent 自管理 + 睡眠期整理记忆
多 Agent 团队共享状态与知识Letta（共享块）/ Graphiti（共享图谱）前者即时同步的内存块，后者结构化的共享事实图谱
医疗/金融合规：需要完整审计轨迹与证据链Zep（失效不删除）或 Mem0（SOC2+HIPAA 托管）前者保留全部历史状态，后者提供合规认证
已在 LangGraph 技术栈内LangMem（候补）零额外基础设施，但非独立框架（1.7K★）
从原始文档/代码库构建组织知识图谱（graph-RAG）Cognee（候补）ECL 管线专长，30.7K★，但会话记忆属性弱
给 Claude Code / Cursor 等编码工具装记忆Mem0（CLI/Harness）或 Letta Code前者外挂式，后者记忆优先的编码 Agent + git 化上下文仓库
💡 组合建议（针对 Agent Workspace / 容器化 Agent 场景）
三者并非互斥。一个务实的组合：Mem0 做用户偏好层（低成本、快接入）+ Graphiti 做业务事实层（时序敏感数据），通过 MCP 端点统一暴露给容器内 Agent（Graphiti 每服务器内置 MCP 端点，Mem0 有官方 MCP 集成）。若你的平台本身就是 Agent 运行时（如基于 OpenCode serve API 的 Workspace），则 Letta 的"记忆块 + 服务化 Agent"模型更贴近你的架构，可直接借鉴其 core/recall/archival 分层设计而非引入整个运行时。
